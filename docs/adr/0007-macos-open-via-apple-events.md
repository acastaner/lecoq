# macOS file-open is delivered through Apple Events, not argv

On macOS a file double-clicked in Finder, sent with "Open With", or passed to `open -a lecoq` is **not** placed in `argv`; the OS launches (or wakes) the app and delivers the path through the `kAEOpenDocuments` Apple Event. lecoq reads its launch path only from `std::env::args_os().nth(1)` ([startup.rs](../../crates/lecoq/src/startup.rs)), so on macOS that path never arrived, and AppKit's default handler — reached because winit's app delegate implements no `application:openURLs:` — showed the user "zimged cannot open files in the 'PNG image' format" for every format. We fix this by registering our own `NSAppleEventManager` handler for `kAEOpenDocuments` (and `kAEReopenApplication`) and feeding what it receives into the **existing single-instance `Inbox`** as an [`Arrival`](../../crates/lecoq-platform/src/instance.rs): `odoc` → `Arrival::Open(first path)`, `rapp` → `Arrival::Raise`. The app already drains `take_arrivals()` every frame, so no app-side code changes; the macOS objc2 glue lives behind a no-op-by-default `SingleInstance::install_open_event_source` trait method, keeping the headless Linux gate green. The handler is installed from an `NSApplicationWillFinishLaunchingNotification` observer that startup registers before eframe starts, because a document that *launches* the app is delivered during `finishLaunching`, before `applicationDidFinishLaunching`.

Found while testing the v0.1.4 DMG (macOS packaging, present since v0.1.0, never carried this handler). v0.1.5 shipped the handler registered too late (see the first rejected option): a double-click that launched zimged still showed the error, and only a file opened while it was already running got through. v0.1.6 registers at will-finish-launching.

## Considered Options

- **Register the handler from eframe's app-creation closure (shipped in v0.1.5).** Rejected after testing on a Mac. That closure runs from winit's `applicationDidFinishLaunching:`, and Apple documents that when the user launches an app by opening a file, the open is handled *before* did-finish-launching. AppKit's default handler had already rejected the launch document by the time ours was registered. Apple's `NSApplication` docs name will-finish-launching as the place to register custom Apple Event handlers; winit's delegate does not implement it, so we observe the notification AppKit posts instead.
- **Register the handler directly in `main()` or eframe's `event_loop_builder` hook, before `NSApplication` finishes launching.** Rejected: that is before AppKit has installed its own default handlers, and nothing guarantees ours survives them. The will-finish-launching notification is the documented point that comes after AppKit's setup and before the launch event.
- **Register an `NSApplicationDelegate` implementing `application:openURLs:`, as winit's own macOS docs recommend.** Rejected: winit 0.30.13's docs are stale. `EventLoop::new` unconditionally calls `setDelegate` with winit's own `WinitApplicationDelegate` (`event_loop.rs:240`), so an app-set delegate is clobbered, and winit's delegate implements only `applicationDidFinishLaunching:`/`applicationWillTerminate:`. Fighting winit for ownership of the delegate is fragile across winit versions. `NSAppleEventManager` registration is independent of the delegate and collides with nothing winit installs.
- **Wait for a winit or eframe open-file event.** Rejected: neither exposes one. winit 0.30's only file events are drag-and-drop (`DroppedFile`/`HoveredFile`); eframe 0.37 has no open-documents hook. There is nothing to wait for.
- **A second, macOS-only delivery channel into the app instead of reusing the `Inbox`.** Rejected: `Arrival::Open`/`Arrival::Raise` already model exactly "open this file" / "just raise the window", with a per-frame drain and a wake callback. A separate channel would duplicate that for no gain and give the app two merge points to reason about.

## Consequences

- A macOS Finder/Open-With **cold launch** opens the file as an arrival *after* the window exists, so it cannot use the pre-window first-image decode that the §1.2 cold-start budget relies on (that path needs the argv file, which macOS does not provide). The window appears briefly empty with the plain "lecoq" title, then the image loads. Launching with the path in `argv` (terminal, `open -a lecoq --args <file>`) keeps the fast pre-window decode.
- [startup.rs](../../crates/lecoq/src/startup.rs) calls `install_open_event_source` before `eframe::run_native`, where it only adds the will-finish-launching observer; the Apple Event handlers go in when AppKit posts that notification. A launch-time arrival therefore lands in the `Inbox` before the window, and before `set_wake`; the first frame's `poll_instance` drains it. That timing can only be confirmed on a Mac, since the gate runs on Linux.
- On macOS the socket single-instance hand-off (§8.4) is largely vestigial: the OS refuses to launch a second bundle instance on double-click and routes the open to the running app via Apple Event instead. The socket code stays (it is cross-platform Unix) but is not the macOS delivery path.
- Only the first file of a multi-file `odoc` is opened, matching lecoq's existing single-image-at-a-time rule (drop of several files opens only the first, [input.rs](../../crates/lecoq/src/input.rs)).
- The objc2 handler is thin glue verified manually on macOS; the file-URL-list → `Arrival` mapping is a pure function unit-tested on any platform. `objc2 0.6` and `objc2-foundation 0.3` were already workspace deps; `objc2-app-kit 0.3` (for the notification name) is a new direct dependency of `lecoq-platform` on macOS, but adds no crate: eframe already pulls it in. All three match eframe's own objc2 stack.
